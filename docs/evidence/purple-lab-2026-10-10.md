# 선택형 WAF·Splunk 실습 검증 기록 · 2026-10-10

기본 ARTEX·PostgreSQL 설치와 분리한 로컬 실습 환경에서 Juice Shop 앞단의 WAF, 실제 감사 로그 수집, Splunk 탐지 규칙과 ARTEX의 로그 조회를 확인했습니다. 이 검사는 독립된 환경 확인이며 ARTEX AI 진단이나 재검증 실행을 대신 완료하지 않습니다. 실행 방법은 [실습 가이드](../purple-lab.md)에 있습니다.

## 검증 환경과 범위

- 별도 Compose 프로젝트: `artex-purple-lab`의 Juice Shop·ModSecurity/OWASP CRS WAF·로그 수집기·Splunk.
- 진단 대상: `http://purple-lab-target:8080`. 브라우저 주소는 `http://localhost:18790`이며 WAF를 통과합니다.
- 실제 로그: WAF native 감사 원문을 정규화하여 `artex_lab` 인덱스의 `artex:lab:audit`로 수집했습니다. 경보는 실제 Splunk saved search의 log event action으로 `artex:lab:alert`에 기록했습니다.
- 검색 계정: 실습 인덱스만 조회하는 `artex_lab_search`. ARTEX는 정확한 실습 인증서 SHA-256 핀으로 관리 API에 연결했습니다.
- 수집기 인증 마운트는 HEC 토큰·인증서 핀 두 파일의 읽기 전용 접근으로 제한했습니다. 관리자·검색 계정 비밀번호 폴더를 수집기에 전달하지 않습니다.
- 기존 취약점 3번과 원래 대상 `juice-shop:3000`은 변경하지 않았습니다. WAF 자산은 새로 등록했습니다.

각 사례에서 정상 대조 요청 `/`, 정보 노출 경로 `/ftp/acquisitions.md`, SQLi 패턴이 포함된 검색 요청을 한 번씩 보냈습니다. `/ftp` 보호는 명시적인 실습 규칙 `1001001`이며 SQLi 검사는 표준 CRS 규칙 `942100`을 확인했습니다. 경보는 이 두 종류의 일치 조건에 대해 생성합니다.

## 실제 환경 확인 결과

`./scripts/purple-lab.sh check`는 실제 WAF 조치와 Splunk 검색 결과를 비교했습니다.

| 사례 | WAF 모드·경보 | 감사 이벤트 | 실제 Splunk 경보 | 확인한 조치 |
| --- | --- | --- | --- | --- |
| 탐지 전용 | DetectionOnly·on | 3 | 2 | 정상·검사 대상 요청 모두 허용, 검사 대상 두 요청의 경보 확인 |
| 실제 차단 | On·on | 3 | 2 | 정상 요청 1건 허용, 검사 대상 요청 2건 차단, 두 차단 경보 확인 |
| 경보 비활성 | DetectionOnly·off | 3 | 0 | 감사 3건 허용, 해당 실행의 경보 없음 |
| 합계 | 9회 요청 | 9 | 4 | 감사·경보 합계 13건 |

정상 대조 요청은 WAF 규칙 일치 없이 통과했습니다. 차단은 native 감사 로그의 명시적 interception과 활성 엔진 모드를 근거로 확인했으며 HTTP 상태 코드만으로 추정하지 않았습니다. 경보의 원본 감사 ID·UUID·조치·시각·규칙 목록도 해당 감사 이벤트와 일치했습니다. 검사 후 정책은 DetectionOnly·경보 on으로 복원했습니다.

탐지 전용 SQLi 요청의 백엔드 응답은 HTTP 500이었습니다. 여기서 확인한 것은 SQLi 패턴 탐지와 WAF 정책 조치이며, SQLi 악용 성공이나 자료 유출을 입증하지 않습니다. `/ftp` 경로 차단 역시 앞단 정책의 효과이고 Juice Shop 내부 취약 코드가 제거됐다는 증거는 아닙니다.

## ARTEX 커넥터의 실제 조회

새 실습 Splunk의 검색 전용 계정으로 `securitysource.Fetch`를 실행했습니다. 각 사례의 실행 UUID와 시작 30초 전부터 조회 시점까지를 지정했으며, 운영 DB나 기존 로그를 변경하지 않았습니다.

| 사례 | 수집 이벤트 | 감사·경보 | 조회 완료 | 검색 경고 | 조치 분포 |
| --- | --- | --- | --- | --- | --- |
| 탐지 전용 | 5 | 3·2 | true | 0 | allowed 5 |
| 실제 차단 | 5 | 3·2 | true | 0 | allowed 1·blocked 4 |
| 경보 비활성 | 3 | 3·0 | true | 0 | allowed 3 |

차단 행의 `blocked 4`는 두 요청의 감사 2건과 경보 2건을 합한 이벤트 수입니다. 네 번의 요청이 차단됐다는 뜻은 아닙니다. 경보 0건의 실제 Splunk 종료 응답도 정상 완료로 해석했습니다.

과거 조사 함수 `FetchInvestigation`도 마지막 사례 시작 30초 전부터 조회 시점까지 실행했습니다. 대상은 `purple-lab-target:8080`, 경로는 전체이며 UUID로 좁히지 않았습니다. **20건 수집, 조회 완료 true, 잘못된 이벤트 0건**을 확인했고 저장한 필드 매핑으로 다시 생성한 쿼리는 원래 쿼리와 같았습니다. 이 20건은 해당 기간·대상의 조회 결과이며 위 세 사례의 13건 집계와 범위가 다릅니다.

실제 Splunk JSON 자동 추출과 `spath`에서 생기는 동일값 중복은 `mvdedup`으로 제거합니다. 서로 다른 값은 보존하여 보수적으로 처리하며, 일반 텍스트의 기존 추출 필드를 버리지 않습니다. 검색 결과 시각은 숫자 오프셋과 마이크로초를 포함하도록 요청하여 모호한 시간대 약어를 추측하지 않습니다.

수정한 앱을 다시 빌드한 뒤 `connect`를 재실행하여 같은 실습 연결을 재사용했고, ARTEX 화면에서도 연결 테스트 성공을 확인했습니다. 연결 테스트는 관리 API의 통신·인증을 확인한 결과입니다. 아래 화면과 별도로 위 수집 함수의 실제 조회를 수행했습니다.

| `go vet ./securitysource ./investigation` | 통과 |
| `./scripts/local-test.sh` | 별도 임시 PostgreSQL을 사용하는 전체 격리 회귀 검사 종료 코드 0; 상위 테스트 156개·실패 0개 |
| 로컬 ARTEX 앱 재빌드·재연결 | 빌드 종료 코드 0, 기존 실습 연결 재사용과 화면의 연결 테스트 성공 확인 |

이 기록의 Go 검사는 운영 DB와 분리한 임시 컨테이너·테스트 DB에서 실행했습니다. 실제 Splunk 조회는 별도로 실습 인스턴스에 읽기 요청만 수행했습니다. 최종 상태는 WAF DetectionOnly, Splunk·수집기 healthy, 전달 대기 0건이었습니다.

수집기 비밀 마운트를 두 파일로 제한한 뒤 컨테이너를 재생성하고 새 정상 요청의 감사 1건이 실제 Splunk에 전달되는지도 확인했습니다. 이미 활성화된 경보에 `alerts on`을 다시 실행해도 기존 탐지 시작 시각과 쿼리가 유지됐습니다. `off → on` 전환만 새 시작 시각을 설정합니다.

## 공개한 자료와 한계

공개 자료는 실제 화면과 결과 수치·검증 범위입니다. API 키, 비밀번호, JWT·개인키, 원본 감사 로그, 전체 검색 내보내기, 운영 DB는 포함하지 않습니다. 원본 확인 기록과 전체 로그는 Git에서 제외한 `evidence-local/purple-lab/`에, 실습 인증 정보는 `.local-runtime/purple-lab/`에 보관합니다.

이 독립 확인 명령이 만든 UUID와 로그를 다른 ARTEX 재검증의 근거로 대신 제출하지 않습니다. 실제 ARTEX 검증은 새 WAF 진단에서 발견한 취약점과 해당 실행의 UUID로 진행합니다. 이번 확인은 기업 환경의 탐지 정확도, 과거 침해 발생·미발생, AI 조사 완주나 자동 사고 확정을 보장하지 않습니다.
